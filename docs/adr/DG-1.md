## 1. Context and Problem Statement

Distributed agent platforms face severe risks when interacting with external tools, adapters, and file systems:
1. **Side-Effect Duplication**: A worker crashes after submitting a command (e.g. `engineering.create_pr`) or losing the acknowledgment. A subsequent retry attempt or agent restart could blindly re-execute the action, creating duplicate PRs, deployments, or payments.
2. **Key Misalignment & Target Tampering**: An agent attempting to retry an action might reuse a cached idempotency key but target a different resource (e.g. changing target repository or branch), corrupting state or executing unauthorized modifications.
3. **Agent Self-Assigned Step Drift**: When an agent process restarts, an LLM might declare a new step name (e.g. `create_pr#2` instead of `create_pr#1`), inadvertently bypassing idempotency deduplication if slots are self-declared.
4. **Outbox Offset Gaps in Database Transactions**: Assigning sequence cursors (`bigserial`) inside write transactions causes dropped events during SSE replay if transaction 11 commits before transaction 10.
5. **Monorepo and Source Scoping Ambiguity**: Projects sharing a single physical repository root could collide or double-count deliverables in portfolio aggregations unless source physical roots and project scopes are decoupled.

DG-1 establishes the authoritative architectural decisions and schema constraints to solve these failure modes prior to executing database migrations.

## 2. Key Derivation and Byte Encoding

### 2.1 Derivation Formulas

| Key Name | Formula | Issuer | Scope of Stability | Purpose |
|---|---|---|---|---|
| `task_intent_key` | `sha256(tenant_id + "\|" + task_id)` | Task Service at admission | All attempts of a task | Delivered as client request token to external providers; prevents duplicate logical task creation across attempts (C01). |
| `operation_key` | `sha256(tenant_id + "\|" + task_id + "\|" + action_slot)` | Action Service | All attempts of a task | Execution journal key; binds approval decision; deduplicates tool side effects across run retries (C29, C29b). |
| `dispatch_idempotency_key` | `sha256(binding_id + "\|" + run_id + "\|" + operation)` | Run Service / Dispatcher | Single run attempt | Submissions and status lookups at provider adapters; preserved across worker restarts (C05, C21). |
| `payload_hash` | `sha256(tool_id + "\|" + arguments_sha256 + "\|" + resource_ref)` | Action Service | Per action proposal | Persisted in `action_executions`; differing hash with same `operation_key` yields `409 OPERATION_KEY_CONFLICT` (C29). |

### 2.2 Canonical Byte Encoding Specification

To guarantee byte-level determinism across programming languages and runtime platforms:
1. **Character Encoding**: UTF-8 without byte order mark (BOM).
2. **String Normalization**:
   - String components are trimmed of leading and trailing ASCII whitespace.
   - Unicode strings must be in Unicode Normalization Form C (NFC).
   - Identifiers (`tenant_id`, `task_id`, `binding_id`, `run_id`, `tool_id`, `action_slot`) must not contain the delimiter character (`|`). If an identifier validation pattern permits pipes, the pipe character must be rejected at input validation.
3. **Hexadecimal Formatting**:
   - `arguments_sha256` must be formatted as exactly 64 lowercase hexadecimal ASCII characters (`[a-f0-9]{64}`).
   - All resulting digest outputs are encoded as 64 lowercase hexadecimal ASCII characters.
4. **Delimiter**:
   - Literal single ASCII pipe character `|` (Unicode `U+007C`, UTF-8 byte `0x7C`).
5. **Null and Empty Component Handling**:
   - If a field is optional, empty, or null (such as `resource_ref` for tools without external resources), it is canonically represented as an empty byte sequence (`""`). The delimiter preceding it is preserved (e.g. `tool_id|arguments_sha256|`).
6. **Hash Algorithm**:
   - SHA-256 per FIPS 180-4.

## 3. `action_slot` Lifecycle and Recovery (C29b)

### 3.1 Definition and Rules
An `action_slot` is a structured business step label (e.g. `create_pr#1`, `run_tests#1`, `export_report#1`).
- **Excludes Resource Target**: The target repository or file path is deliberately **excluded** from `action_slot`. Target parameters belong strictly inside the action proposal payload and `resource_ref`.
- **Authority**: The platform (Action Service / Workflow Orchestrator) holds authority over `action_slot`, **not the autonomous agent**.
  - In orchestrated workflows, the workflow template defines the exact slot sequence.
  - In native agent workflows, an agent may propose a slot, but the Action Service validates it against the declared step list of the task type.
- **Persistence Prior to Execution**: The slot is persistently committed to `task_intents` **prior to the initial tool call**, in the same atomic database transaction as the execution intent.

### 3.2 Recovery and Agent Restart (C29b)
When a run attempt fails, times out, or restarts:
1. The new attempt (new `run_id`, same `task_id`) resumes execution.
2. The Action Service recovers the persisted `action_slot` from `task_intents` matching `(tenant_id, task_id, tool_id, workflow_step)`.
3. If an autonomous agent after restart proposes a new slot name (e.g. `create_pr#2` instead of `create_pr#1`):
   - The Action Service detects that a slot for this logical step was already declared and persisted (`create_pr#1`).
   - The Action Service maps the agent's proposal back to the recovered persisted slot `create_pr#1`.
   - If the task type policy strictly enforces declared slots and forbids undeclared step expansion, any proposal with an unknown slot is rejected immediately with `422/409 ACTION_SLOT_UNDECLARED`.
4. The derived `operation_key` remains identical (`sha256(tenant|task_id|create_pr#1)`).
5. The Action Service checks `action_executions` table: finding an existing execution record, it returns the journaled result without calling the external tool a second time.
6. **Result**: Exactly one PR is created at the provider mock (`mock.prs_created == 1`), satisfying Conformance Case C29b.

## 4. Conflict Handling and Idempotency Invariants (C29, C38)

### 4.1 Identical Operation Key with Matching Payload
When an action execution request arrives with `(tenant_id, operation_key)`:
- If `payload_hash == action_executions.payload_hash`:
  - If state is `succeeded`: return the persisted `result_payload` immediately.
  - If state is `running`: return current execution reference and status (in progress).
  - No external tool or provider invocation occurs.

### 4.2 Identical Operation Key with Conflicting Payload (C29)
If a caller (or agent) attempts to execute an action with an existing `operation_key` but with differing arguments, tool, or target resource:
- `incoming.payload_hash != action_executions.payload_hash`.
- Action Service immediately aborts the transaction and returns:
  `409 OPERATION_KEY_CONFLICT`
- The external provider is never contacted.

### 4.3 Retries During Unknown State (C21, C38)
If a run attempt crashed after dispatching a command to an external provider without receiving an acknowledgment:
- Run state is `unknown` with dispatch intent in `sent` state.
- If a user or scheduler requests `retry_new_attempt`:
  - The Task/Run Service rejects the request with `409 REMOTE_OUTCOME_UNKNOWN`.
  - Retries are strictly prohibited while remote outcome is unreconciled.
- Reconciliation process:
  - If the adapter supports status lookup by `dispatch_idempotency_key` or `task_intent_key`, the worker polls the provider:
    - Provider confirmed executed -> transition `unknown -> running -> succeeded` (or persist execution ref).
    - Provider confirmed absent -> mark attempt `failed`, permitting a clean new attempt.
  - If the adapter does NOT support lookup (`lookup_supported == false`, C38):
    - Run remains in `unknown`.
    - Automated retry remains rejected with `409 REMOTE_OUTCOME_UNKNOWN`.
    - HUD surfaces a blocking attention item for operator intervention.

## 5. Relay Offsets Strictly in Commit Order (ADR-020, C33)

### 5.1 The Gap Problem with In-Transaction Sequences
If database write transactions assign sequence cursors (e.g. `bigserial`) inside the business transaction:
- Transaction A acquires sequence 10.
- Transaction B acquires sequence 11.
- Transaction B commits at $t_1$.
- Transaction A commits at $t_2 > t_1$.
- A real-time SSE client replaying events from sequence 11 reads Transaction B's event. When Transaction A commits later with sequence 10, the client will **permanently miss event 10**.

### 5.2 ADR-020 Architecture
1. **Outbox Without Offset**: Business transactions insert events into the `outbox` table containing event payload and metadata, but **explicitly no offset column**.
2. **Single Relay per Tenant Stream**: An outbox relay worker acquires a PostgreSQL session-level or transaction-level advisory lock (`pg_advisory_xact_lock(tenant_stream_hash)`).
3. **Post-Commit Monotonic Offset Assignment**:
   - The relay polls committed outbox records ordered by transaction commit timestamp / WAL LSN.
   - In a dedicated relay transaction, the relay inserts the events into `event_log`, assigning a strictly monotonic `ingest_offset` per `(tenant_id, stream_id)`.
   - The relay updates projections and publishes to SSE subscribers.
4. **Replay Invariant**:
   - HUD cursors point strictly to `event_log.ingest_offset`.
   - Replaying from any valid cursor produces an identical projection matching fresh state snapshots without gaps or duplicates (C33).

## 6. Physical Sources and Project Scopes (ADR-022, C32)

### 6.1 Architectural Decoupling
To support modern monorepo architectures and prevent deliverable duplication, the platform separates physical repositories from project definitions:
- **`sources` Table**: Represents the physical directory or Git repository on disk.
  - Identified by `source_id`, `canonical_root` (normalized physical path), and `repo_identity` (Git remote or genesis commit hash).
  - Invariant: Exactly one physical directory on disk = one `source_id`.
  - Re-registering the same folder under a different `source_id` yields `409 SOURCE_ALREADY_REGISTERED`.
- **`project_scopes` Table**: Represents the logical project boundary within a source.
  - Identified by `(tenant_id, source_id, metadata_root)`.
  - Invariant: `UNIQUE (tenant_id, source_id, metadata_root)` — exactly one project per `metadata_root`.

### 6.2 Monorepo and Shared Components (C32)
Consider a repository containing `apps/app-a`, `apps/app-b`, and a shared library `libs/shared`:
1. **Single Source**: `sources` record created once for the root directory.
2. **Distinct Project Scopes**:
   - Project A: `metadata_root = "apps/app-a/.ppm"`
   - Project B: `metadata_root = "apps/app-b/.ppm"`
   - Shared Component: `metadata_root = "libs/shared/.ppm"` (owned by Project Shared Gateway).
3. **No Double-Counting**:
   - The deliverable for the shared library is owned exclusively by Project Shared Gateway.
   - Project A and Project B reference the shared library using `dependency_refs`.
   - Program and portfolio rollups aggregate verified weight across distinct deliverable IDs; consumer projects never inflate their progress denominator.
4. **Independent Scans (C32)**:
   - When a note or update in `apps/app-a/.ppm` is modified, the collector rescans.
   - Only Project A receives a new assessment proposal and updated assessment ID.
   - Project B and Shared Gateway detect identical scope hashes and bypass reassessment, retaining their prior assessment IDs and updating only `last_successful_scan_at`.

## 7. Decision Alternatives and Trade-Off Analysis

### 7.1 Key Derivation and Payload Hashing
- **Options Considered**:
  - *Option A (Chosen)*: Deterministic pipe-delimited UTF-8 string hashed with SHA-256; separate `operation_key` (intent) and `payload_hash` (content).
  - *Option B*: JSON Canonicalization Scheme (RFC 8785) over an object containing all fields.
  - *Option C*: Hash of raw request body from caller.
- **Rationale for Option A**:
  - Extremely lightweight, zero external library dependency, microsecond evaluation in high-throughput loops.
  - Decoupling `operation_key` (step) from `payload_hash` (parameters) is essential to detect `OPERATION_KEY_CONFLICT` (same step, changed target).
  - RFC 8785 JCS is reserved for complex approval digests (`action_digest`); key derivation requires simple fixed-order field concatenation.
- **Rejection of Option C**: Callers may alter whitespace or send non-deterministic JSON field ordering, breaking idempotency.
- **Reversibility**: Low. Database uniqueness constraints and indexes rely on key structures. Changing requires schema migration and hash recomputation.
- **Evidence that would alter decision**: Proof of delimiter injection vulnerability despite identifier validation rules, in which case length-prefixed encoding would be adopted.

### 7.2 Action Slot Authority
- **Options Considered**:
  - *Option A (Chosen)*: Platform workflow issues/validates slot; persisted in `task_intents` prior to tool execution; recovered on restart; agent-proposed slots mapped back or rejected.
  - *Option B*: Autonomous agent self-assigns slot strings without platform validation.
- **Rationale for Option A**: Autonomous LLMs frequently drift or rename steps upon restart (e.g. `create_pr#2`). Allowing the agent to assign slots creates duplicate external side effects (C29b).
- **Rejection of Option B**: Directly causes side-effect duplication in retry loops.
- **Reversibility**: Moderate.
- **Evidence that would alter decision**: None. Strict side-effect safety is non-negotiable.

### 7.3 Outbox Relay Offset Assignment
- **Options Considered**:
  - *Option A (Chosen)*: Single relay per tenant stream holding advisory lock; assigns monotonic `ingest_offset` post-commit in commit order.
  - *Option B*: In-transaction sequence generator (`bigserial` / PostgreSQL `nextval`).
  - *Option C*: Distributed logical clocks (e.g. HLC / Vector Clocks).
- **Rationale for Option A**: Guarantees zero gaps in SSE cursors without requiring distributed coordination or complex gap-repair client protocols.
- **Rejection of Option B**: Subject to race conditions where transaction 11 commits before 10, causing clients to permanently skip 10.
- **Rejection of Option C**: Adds immense client-side complexity for single-node / pilot deployments.
- **Reversibility**: High. If relay throughput bottlenecks beyond 10,000 events/sec, partitioning by stream ID or using PostgreSQL `pg_snapshot_xmin` watermarks can be introduced.
- **Evidence that would alter decision**: Benchmarking in P1a-WP7 showing single relay throughput failing to meet 200 events/s requirement.

### 7.4 Physical Source vs Project Scope Decoupling
- **Options Considered**:
  - *Option A (Chosen)*: Decoupled `sources` (physical filesystem root) and `project_scopes` (logical metadata root).
  - *Option B*: Monolithic location registration equating one physical root to one project.
- **Rationale for Option A**: Essential for monorepos, multi-project repositories, and shared enterprise libraries.
- **Rejection of Option B**: Forbids monorepos; requires duplicating repository checkouts on disk.
- **Reversibility**: Low. Fundamental data model design.
- **Evidence that would alter decision**: None. Monorepos are an explicit enterprise requirement.
